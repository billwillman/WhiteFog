# Unity 技能工作台设计复盘

## 从 0.317 秒的飞剑说起

在「基础剑法」的时间轴上，策划选择 0.317 秒的动作，只看到「原作表现事件 / 发射飞剑」。这一行能回答何时出手，却回答不了从哪个挂点发出、使用哪个预制体、飞多快、接触受击体后发生什么。把其中一发改成另一种投射物，本应是编辑这一行的工作。

## 这次在设计上错在哪里

| 设计决定 | 给策划带来的实际问题 | 应采用的设计 |
| --- | --- | --- |
| 把某招的成品表现当成动作类型，命名为「发射飞剑」 | 飞剑、飞针和法球原本可以共用飞行逻辑，却看起来每一种都需要程序增加一个选项 | 动作叫「产生投射物」。飞剑由节点上的预制体、拖尾、轨迹、速度、挂点和命中表现定义。保留原招作为可编辑的配置样例。 |
| 多个发射节点共用技能图上的一组资源和运动参数 | 改第二发的速度可能同时改掉第一发和第三发，复制节点也看不出共享边界 | 每个节点拥有自己的属性。旧图允许读取原配置，在首次编辑该节点时保存本地属性。共享的 Prefab 依然复用，修改引用和修改资源本身是两种操作。 |
| 用「原作表现事件」打包角色动作、特效、投射物、记录标记 | 看时间轴无法辨认哪些行会播放资源、哪些行只是记录。读取轨道序号还要求策划了解导入器内部排列 | 添加菜单直接列出能力，时间轴显示实际动作名。追溯来源用技能 ID 和原轨道数据，日常编辑直接选择资源。没有执行行为的导入标记在界面上明确说明。 |
| 把施法、飞行和命中都归到施法者的时间轴 | 固定时刻的命中会在改速度或改距离后错位。打断时，一刀切地取消后续事件还可能让已出手的投射物失效 | 施法者负责发射前的等待，投射物负责飞行。命中盒在有效时间内接触当时的受击体才触发下游。下游延迟从接触起算。到达终点或目标消失可直接落空。打断只取消尚未释放的部分。 |
| 条件在界面上宣称「每次执行前检查」，却允许动作走不同的调度入口 | 会出现同样的条件对普通动作生效，对特殊发射失效。策划无法靠配置解释结果 | 同一个条件使用同一套求值逻辑。把「是否允许出手」放在发射节点，把「接触后是否允许结算」放在下游节点。 |
| 把「触发一下」和「播放多久」画成同一种时间标记 | 动画持续、状态混合和瞬时发射在同一行上难以区别。不同 Animator 参数还会走不同长度的路径 | 瞬时事件标时点，持续动画标区间，混合段单独着色。预演按当前参数求路径，等待外部 Trigger 时显示待定。此项在前一次工作台迭代完成。 |
| 把试放用的施法者、敌人和伤害输入隐含为技能规则 | 试放里看到飘字，并不能证明技能已配置命中公式；新建动作把施法者也默认连到目标，更会把问题伪装成挂点或朝向错误 | 施法者、目标是显式实体输入。测试场景提供样例演员，试放来伤独立标识。有命中连线时，由图中的动作决定结果。 |
| 只看原作样例能否播出来，忽略空白图的创作流程 | 已导入技能可以演示，但策划新建技能时可能找不到同一个能力，或者必须先有特定技能图类型 | 从空白技能走一遍「添加动作 → 配置 → 接条件与结果 → 保存重开 → 试放」。导入技能再用同一套操作做局部修改。 |

## 站桩演示掩盖了哪条设计错误

旧飞剑飞向出手时记录的位置，却在结束时读取目标的新位置播放命中特效。静止木桩上两点重合，玩家看不出错误。敌人侧移后，这套做法会让剑扑空而人物掉血。把“飞够了多久”当成“打到了谁”是建模错误。

投射物的移动轨迹、命中盒和命中后的技能动作分别配置。直线或追踪决定投射物怎么飞。盒子的尺寸、局部偏移、开启时间和有效时长决定哪些空间和时间可以发生接触。目标侧的受击体随角色移动；在有效时间里做重叠检测和逐步扫掠，接触才触发一次下游动作。飞行结束可以零命中。换轨迹不应迫使策划更换判定机制。

例如，敌人在飞剑到来前横移出路径，应当满血；敌人提前移到路径中段，可以在终点之前受击。窗口已经关闭时，即使模型相交也不会结算。瞄准后排时，「确定目标」只接受后排实例；「非确定目标」先按 MCC 实体标签筛选，再取沿途最先接触的合格受击体。两者都能落空。

## 怎样验收通用性

1. **换资源**。同一个「产生投射物」动作分别绑定飞剑和另一件预制体，两者都能试放。
2. **改一发**。在同一张图放两个发射节点，单独修改第二发的速度、挂点或拖尾，检查第一发。复制技能、保存、重开后再检查。
3. **改时序**。固定发射时刻，改变距离或速度，观测接触时刻怎样变化。命中动作的延迟从实际接触开始计算。
4. **改条件**。在出手前使前置条件失效，以及在出手后打断施法者，分别核对发射数量、接触次数和扣血次数。
5. **区分演示与规则**。将预览来伤调大，同时为命中连接一条明确的数值动作。一次有效接触只产生图中指定的结果。
6. **回看原招**。用同一旧技能对比改动前后的资源、发射时刻、飞行参数和抵达表现；打开工作台查看属性也不应写回整张技能资产。

## 工作台整体检查范围

核对了 18 种动作和 11 种条件的接口描述，以及编辑页、节点图、Buff、公式与数值、快速试放和当前场景试放的入口。Buff 资产、周期效果图、等级表和结算公式已有自己的选择入口，继续用引用表达共享关系。旧的实例化和音效动作仍使用 Resources 路径，通用动画动作仍保留 Legacy 接口；这两处依赖名称的设计仍有编辑成本。改动优先落在投射物、资源挂接、触发条件和试放上。

角色受击体由同一物体上的 Collider 和 MCC Demo 的 DamageReciever 组成。工作台的「战斗 / 受击体」继承 DamageReciever，可直接使用已有的 Demo 角色。预览场给两方角色配置了可编辑的触发盒。运行时仅检查已启用的受击体，使用投射物配置的层、尺寸和偏移。设计新敌人时需按该模型调整受击范围。

本次团结编辑器 Play Mode 验证覆盖了四个原作技能的试放，以及普通命中、目标横移、路径中段接触、发射后打断并销毁释放实例、命中盒提前关闭、发射前置条件失败、追踪、跨帧高速穿越、排除受击层、尚未开启窗口、停用受击体。工作台 UI 之外各通用节点的每一种参数组合未逐一实播。


## 把瞄准对象一直传到扣血动作的问题

最初只拿原目标测试碰撞。即便有别的敌人挡住，命中回调仍闭包引用原目标。只改外层碰撞检测，会出现前排接触、后排扣血的错误。MCC 的 `VerifyObject → DealDamage(碰到的实体) → SetTargetEntity` 已经演示了该传哪个对象。现在工作台把每发实际接触者交给命中分支，结算和试放回调都读取它。复制节点会分别复制其筛选标签。

做下一个技能前，先把原包中的执行器、目标来源、过滤顺序、状态所有者和结算入口对照到一张实际技能图上，再决定上层需要补什么。完整对照和前后排案例见[技能平台设计与 MCC 边界](Tuanjie技能平台设计与MCC边界.md)。

本次在隔离的团结工程中用工作台构造技能图并进入 Play Mode，完成 18 项前后排用例。其中包含高速跨过多个目标、复合 Collider、死亡与停用、原生受击体、发射后打断、图连线与试放回调，以及固定伤害和公式伤害对实际受击人的结算。公式测试在出手后改变施法者攻击，前后排设置不同防御，核对施放时攻击和接触对象防御。另复跑 11 项原有投射物检查及 4 项原作技能试放。
